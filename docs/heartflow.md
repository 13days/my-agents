# 助理

助理将飞书用户身份可读取的消息转成可审核的行动建议。入口是面板的「助理」，已有机器人继续承担私聊通知和卡片确认。未经 check 的建议不执行。

## 使用

1. 在指定协调节点安装 bytedcli，完成用户身份授权。历史消息需要 `offline_access`、`im:chat:read`、`im:message:readonly`、`im:message.group_msg:get_as_user`、`im:message.p2p_msg:get_as_user`。机器人授权不能替代用户授权。
2. 助理 → 接入设置：搜索并选择群聊，或者输入已知的私聊 / 群聊 chat_id。设置读取起点、同步间隔及分析模型。模型复用当前节点的 Codex 账号池；不调用 CLI 工具执行分析。
3. 同步并生成建议。模型参考来源、邻近讨论、引用消息、已有事项、会话列表以及启用学习的 check 记录。模型输出只是草稿；不合规的来源和不存在的目标会被过滤。
4. 待确认中修改摘要、关联多个事项，增加多个行动。每个行动可以选择已有会话，或指定机器和目录创建新任务。支持部分批准、拆分、合并、暂缓、忽略。
5. 批准后追加排队，执行动态显示投递及结果。check 保存修改前后版本、批准行动和原因，可单独停用学习参考。反馈不会自动扩大执行权限。
6. 若需要飞书内确认，填写 IM 接入中已配对的机器人用户 open_id，并开启通知。它可能与用户授权应用的 open_id 不同。配置可访问的面板地址，卡片可打开网页进行复杂修改。不要在地址中放令牌。卡片也携带建议版本，旧卡片不能批准更新后的内容。

## 数据和执行边界

- `core/heartflow-store.js`：本机 `panel-heartflow.json`，0600 权限、同步落盘、原子替换，保存消息、事项、建议、check 和投递记录。
- 多对多由建议的 messageIds、matterIds 和独立行动 / 投递记录连接。批准后的行动保存在 deliveries 和 check.approvedActions，不能因建议继续编辑而改变。
- `core/heartflow-feishu.js`：通过 argv 调用用户身份 CLI，不用 shell 插值。每页 50 条，每个聊天单轮最多 4 页，保留继续游标；最近五分钟回看去重，补拉引用消息。历史编辑超过回看窗口不保证即时发现。
- `core/heartflow-model.js`：通过现有模型中继请求，无执行工具，流式读取有超时及大小限制。每次分析最多 30 条触发消息。支持资料消息不会被视为扩大权限的指令。
- `core/heartflow.js`：版本化 check、投递占用、会话队列、结果核对。修改过的来源会阻止尚未投递的旧行动；已经开始的行动不会因为来源变化被自动撤销。
- 飞书通知经过现有 IM 主节点，check 回到对应助理协调节点。通知发送结果不明时不自动重发。

## 首版范围

使用选定聊天的轮询，不是全账号消息实时事件订阅。私聊需要提供对应 chat_id；群聊支持名称搜索。图片、文件和合并转发内容未做视觉或附件解析，页面保留类型提示；重要信息需要查看原消息。

学习目前是检索相关 check 作为模型上下文，不是微调。模型可能漏判或误判，消息页可以人工建立建议。暂缓需要手动重新处理，没有自动到期执行。

助理只在你配置的节点协调，数据不参与集群快照复制；不要在多节点重复开启同一监听范围。协调节点离线时暂停处理。其他节点可以执行批准任务，但不能接管审批记录。

本机投递记录能防止重复点击和服务恢复自动重放，不承诺网络分区下的 exactly-once 执行。投递结果不明确时显示“结果待核对”，先查看原会话，禁止自动重试。已经批准但尚未开始投递的记录在恢复后继续处理。

### 执行历史核对与卡片更新

待确认建议会读取关联会话最近 80 条用户/助手记录；记录变化时重新核对，批准前再次核对。模型必须引用实际记录，区分已经发起、已完成、被后续决定替代。逐项消除已覆盖的行动，其余行动保留；原版本的批准失效。核对结果与原文依据显示在执行动态中。实时记录不可读时阻止批准，不使用缓存快照推断完成。此核对只覆盖已关联会话及最近记录，并非全库检索。

发送人身份、自身澄清、引用与时间共同参与合并判断。通知保存机器人返回的消息 ID，后续版本更新同一张卡；更新失败不另发卡。旧版未保存消息 ID 的卡片无法自动定位，因此停止继续发送同一建议的新卡，旧按钮仍受服务端版本校验。修改行动范围后需先保存，再批准，让执行历史核对覆盖新范围。

群聊后续结论现在独立于会话历史核对：沿明确回复链和话题关联读取最多 100 条消息，提供发送人 ID、已解析姓名、时间与原文。模型仅能用真实引用将明确撤销的行动标为被替代；无法从群聊声称代码已执行。消息内容或关联后续变化会触发重新核对，批准前也会核对。此范围暂不覆盖无引用、无话题关联且尚未合并到建议的跨聊天结论。

发送人姓名使用消息本身及 @ 提及中的明确 ID 对应关系补全；同步时分批补读旧消息元数据。没有依据时显示“姓名未解析”，不猜测姓名或职级。消息列表同步显示关联建议的处理状态和撤销原因，避免仅展示已读消息却无法看出处理结果。

### 按话题理解（而非仅识别 @）

初次分流纳入自己的消息与承诺，@ 不作为入口门槛。后续核对提供原始来源、明确回复链、同群最近七天内最多 80 条候选，以及选定聊天中共享具体 URL 的最多 20 条跨群候选，总量最多 150 条。原始来源优先保留。候选只是供模型理解的上下文，必须区分并行话题，不能仅因同群、同人或共用链接就判定同一任务。

模型可保存话题最新状态（讨论中、已形成决定、范围变化、撤销、群内报告完成）和逐字引用；页面展示这些依据。范围变化要求先核对并保存行动才能批准。群内报告完成不等于执行系统确认完成。没有引用/共享链接的跨群语义关联、超过窗口的历史仍可能遗漏，尚未建立全量向量检索。

页面入口为 `/assistant`，旧 `/heartflow` 链接仍兼容。内部存储名、接口与卡片回调标识保留，已有消息、建议、反馈和审批版本无需迁移。
